How I track this website

These are the steps that I follow on this practice site. I wrote them down to learn the method. This is also a long page, so I use it to test scroll depth tracking.

I start with a question

Before I make a tag or a report, I write down what I want to know. A specific question gets a useful answer. "Do visitors who read the guide also send the contact form?" is better than "How is the site doing?".

I ask these questions:

  • What do I want to know, and why?
  • Which event or metric shows the answer?
  • Which report will show it, and how often will I look at it?

I write my questions on the Report requests tab of my practice spreadsheet.

I write the tracking plan

Each business question becomes one or more events. For each event, I write the name, the parameters and the trigger. I use the GA4 recommended event names when one fits, because GA4 then gives better reports.

To practise for bigger projects, my spreadsheet has room for many websites. Each site has its own status column: Live, Planned, Broken or Not needed. The other sites in it are invented examples.

See the Sites and Event plan tabs of my spreadsheet.

I install Google Tag Manager and use the dataLayer

I put the first GTM code in the head of each page, as high as possible, and the second code just after the opening body tag. Then I add a Google tag with the GA4 Measurement ID.

The dataLayer is a list that the website uses to send information to GTM. On this site, each page sends its page type, and the contact form sends an event called generate_lead.

I build and test one tag at a time

I make one tag, then I test it in GTM Preview mode and in GA4 DebugView. When it is correct, I publish a new GTM version with a clear name and a short note. If I build many tags at the same time, errors are hard to find.

Before I publish, I check 3 things: the tag fires on the correct action, it fires only one time, and the parameters have values.

I check data quality on a schedule

Tracking can break when a website changes, often without a warning. To practise, I check my data on a schedule, not only when I see a strange number.

  • Daily: data arrives, with no day at zero and no sudden drop.
  • Weekly: key events fire one time only, and their parameters are not empty.
  • Monthly: the website's own domain is not a referral, unassigned traffic is low, campaign links have UTM tags, and there is no personal data in the reports.
  • After each change to the site: I test the key events again.

See the QA checklist and QA log tabs. The Summary tab counts the failed checks for each site.

I look for the root cause of tracking issues

When a number looks wrong, I do not fix the first thing that I see. I follow the same steps each time:

  1. I describe the symptom exactly: which report, which site, which dates and how large the change is.
  2. I check if the change is real. A holiday or a post on LinkedIn can change traffic.
  3. I compare with other data, for example the GA4 Realtime report or the same week last month.
  4. I test the tag on the live site with Tag Assistant and DebugView.
  5. I check if I changed the website or the GTM container on that date.
  6. I write down the root cause and the fix.

See the Issue log tab. It also shows how many days each issue was open.

I explain what the data means

A report must answer the question, not only show numbers. I start with the answer in one sentence. Then I show the data that supports it. Then I say what I recommend.

I practise writing for two kinds of reader. The first wants the answer in plain words. The second wants technical detail, for example the event name, the page and the steps to make a problem happen again.

I use segments to compare groups, for example new and returning visitors, or visitors from LinkedIn and visitors from GitHub.

I document everything

I keep my spreadsheet, my GTM version notes and my report notes up to date. Then, months later, I can still explain why a number changed.
